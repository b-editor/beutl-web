# ADR 0003: Forgejo をヘッドレスで置き、beutl-web が代理操作する

## Status

Accepted

## Context

Beutl のプロジェクトはディレクトリ構造で、`.bep` / `.scene` / `.belm` はいずれも
`Beutl.Core/JsonHelper.cs` が `WriteIndented = true` で書き出す整形済み JSON になる。
行単位の差分がそのまま意味を持つので Git と相性が良い一方、素材 (動画・音声・画像・
フォント) は巨大なバイナリで、通常の Git オブジェクトに入れると破綻する。

そこで Beutl のプロジェクト管理基盤として Git サービスを自前で持つことにした。
サーバーは Forgejo をセルフホストする (別リポジトリ `git-server`)。素材は Git LFS に載せ、
その振り分けはリポジトリ作成時に置く `.gitattributes` が担う。

決めるべきだったのは「ユーザーが Forgejo とどう関わるか」だった。

## Decision

**Forgejo の Web UI は一般ユーザーに公開しない。** ユーザー向けの画面は beutl-web だけに
置き、Forgejo は git バックエンドと API に徹する。リポジトリは当面すべて非公開。

この選択から、以下が決まる。

### 1. SSO (OIDC) は入れない

ユーザーが Forgejo に対話ログインしないので、Better Auth を OIDC プロバイダにする必要がない。
`better-auth@1.6.26` には `better-auth/plugins/oidc-provider` があるが (1.7 で
`@better-auth/oauth-provider` へ置換される)、導入すると Prisma に 3 テーブル追加・JWKS 運用・
同意画面が必要になる。ヘッドレス構成ではその全部が不要になる。

将来 Forgejo の UI を公開する判断をしたときに、改めて OIDC 化を検討する。

### 2. beutl-web は管理トークン + `Sudo` ヘッダで代理操作する

`packages/forgejo` が唯一の窓口になる。サイト管理者のアクセストークンで認証し、
`Sudo: <forgejoUsername>` を付けて対象ユーザーとして実行する。こうすると Forgejo 側が
そのユーザーの権限で判定するため、他人の非公開リポジトリは 404 になる。

Caddy は `/api/v1/*` に共有シークレットヘッダ (`X-Beutl-Proxy-Secret`) の一致を要求する。
管理トークンが漏れても壁がもう一枚残る。定数時間比較ではないので、単独の認証手段ではなく
多層防御の 1 枚として扱う。

### 3. Beutl アカウントと Forgejo ユーザーの対応表を持つ

`GitAccount` (userId ↔ forgejoUserId / forgejoUsername)。Forgejo 側のユーザーは
beutl-web が管理 API で作る。ユーザー名は `Profile.userName` を Forgejo の規則に正規化して
採番する。最終的な一意性の判定は Forgejo に委ねる
(`POST /admin/users` の 422 を見て次の候補に進む)。

衝突したときはまず `-2`, `-3` と連番を振るが、5 回外したらランダムなサフィックスに
切り替える。表示名が未設定のユーザーは全員 `beutl-user` から始まるので、連番だけだと
ユーザーが増えるにつれて前の方が埋まりきり、候補が枯渇して発行できなくなる。

メールアドレスは Forgejo が一意性を要求するので、実アドレスは渡さず
`<userId>@users.noreply.<host>` を合成する。

### 4. git 用トークンは管理者向けエンドポイントで発行する

デスクトップは git over HTTPS の Basic 認証にアクセストークンを使う。発行と失効には
**`/api/v1/admin/users/{username}/tokens`** を使う。管理トークンだけで発行も失効もでき、
発行時の応答に平文 (`sha1`) も入る。

紛らわしいことに、`/admin/` の付かない `/api/v1/users/{username}/tokens` は別物で、
書き込みに対象ユーザー自身の Basic 認証を要求する。Forgejo 16.0.2 での実測:

| 操作 | `/users/{u}/tokens` + 管理トークン | `/admin/users/{u}/tokens` + 管理トークン |
| --- | --- | --- |
| `GET` (一覧) | 200 | 200 |
| `POST` (発行) | 401 `auth method not allowed` | 201 (`sha1` あり) |
| `DELETE` (失効) | 401 `auth method not allowed` | 204 |

当初はこの `/admin/` 側を見落とし、発行のたびに `PATCH /admin/users/{u}` で使い捨ての
パスワードを設定して Basic 認証する方式を採っていた。動きはするが、同じユーザーの操作が
同時に走ると後から設定されたパスワードで先の認証が 401 になるため再試行が要り、失敗すると
ユーザーのパスワードを書き換えたまま抜ける。現在の方式はパスワードに一切触らない。

#### 退会したときに何を消すか

Beutl アカウントを消しても、Forgejo 側を消さなければ端末に配ったトークンは生き続ける。
git と LFS の通信は Caddy が素通しして Forgejo が直接認証するので、beutl-web を一切
経由しない。「トークンを発行 → 退会 → 手元のトークンで push」が通ってしまう。

トークンだけを止める手段が無い。失効は上のとおり対象ユーザーの Basic 認証を要求し、
無効化のフラグも効かない (`active: false` と `prohibit_login: true` はどちらを立てても
git のトークン認証を素通しする。16.0.2 で実測)。確実に断てるのは **ユーザーごと消す**
ことだけで、これはリポジトリとトークンも一緒に落とす。リポジトリを持っているユーザーは
`?purge=true` を付けないと 422 で拒まれる。

したがって退会処理は、`GitAccountDeletion` という印を軸に進める。印は 2 相を持つ。

| phase | 意味 | できること |
| --- | --- | --- |
| `BLOCKING` | 退会を始めた | 資格情報の発行を止める。**purge はしない** |
| `READY_TO_PURGE` | Beutl 側のユーザーが実際に消えた | purge してよい |
| `NEEDS_REVIEW` | 自動では決着できない | 何もしない。人が確認する |

相を分けるのは、ローカルのユーザー削除が失敗しうるため。`BLOCKING` のまま purge すると、
まだ生きている利用者の Forgejo アカウントとリポジトリを消してしまう。`READY_TO_PURGE`
への遷移はユーザー削除と**同じトランザクション**で確定させる。

1. `beginGitAccountDeletion` — 印 (`BLOCKING`) を書き、身元を確かめ、トークンを失効
   させる。**ここが成否の分かれ目**で、失敗したら Beutl 側も消さずに中止する
2. Beutl 側のレコードを消し、同じトランザクションで `READY_TO_PURGE` にする
3. `finishGitAccountDeletion` — 身元を確かめ直し、掃き直して purge する

印は対象が見つかる前に書く。Git を使っていないように見えても、その直後に初回の
プロビジョニングが走ることがあるため。印があれば発行は止まり、片付けの段でもう一度
探し直せる。`forgejoUsername` を null 許容にしているのはこのため。

3 では**控えた名前を直接引く**。合成メールで探し直すと、Forgejo のホスト名が変わった
ような場合に「見つからない = 片付いた」と誤って結論し、実在するユーザーと生きた
トークンを残したまま印を消してしまう。

消す相手は **id と合成メールの両方**が控えと一致するものだけ。これは復活の照合でも
同じで、**メールは一致するが id が違う相手は「確認済み」にしない**。生きたトークンを
残したまま見終わったと数えると、復元後の公開判定がそれを 0 と読む。人の確認に回す。

削除は取り返しが
つかないので、通常操作より 1 つ厳しくする。片方でも違えば `NEEDS_REVIEW` に落として
人に確かめてもらう。

復元でアカウントが戻っても id は変わらない (同じ行が戻る)。id が違うのは
「消して作り直された」など、こちらの控えでは説明が付かない事態なので、自動では
決めない。控えに id が無いのは、対応表を失った状態で合成メールから引き当てた古い行
だけで、その場合はメールで判断する (それ以外に手掛かりが無い)。

控えた名前で見つからない場合は、合成メールで引き直してから結論する。名前だけで
諦めると、復元先で改名された本人を「もう居ない」と誤って結論する。ただし引き当てた
相手にも同じ 2 点照合を課す。この規則は退会の経路と復活の照合で同じ。

準備の段階 (1) で失敗したとき、および 2 のトランザクションが失敗したときは
`BLOCKING` の印を取り消す。利用者はまだ生きているので、印が残ると二度と資格情報を
発行できなくなる。

取り消せるのは**自分が立てた印だけ**。行は `userId` で 1 つしか持てないので、同じ
利用者の退会要求が 2 本走ると共有することになる。片方の失敗でもう片方の印を消すと、
進行中の側が印を失ったまま利用者を削除し、その後に発行されたトークンが Forgejo に
残る。そこで `intentId` を持たせ、一致するときだけ消す。2 の `READY_TO_PURGE` への
遷移も 1 件更新できたことを確かめ、できなければトランザクションごと巻き戻す。

#### 印には期限を持たせる

`intentId` だけだと、印を立てた処理が消えたときに誰も進められなくなる。1 の直後に
Worker が落ちる、デプロイで打ち切られる、タイムアウトする — どの場合も `BLOCKING` の
行が残り、その利用者は資格情報も発行できず、退会をやり直すこともできない。定期実行は
`READY_TO_PURGE` しか見ないので、放っておいても解けない。

そこで `leaseUntil` を持たせる。**期限内は他の処理が触らない。切れていれば、握っていた
処理は落ちたものとして引き取れる。** 引き取りは条件付き更新 (`phase = BLOCKING` かつ
期限切れ) なので、同時に来た 2 つのうち 1 つしか成立しない。引き取られた側は
`markGitAccountDeletionReady` が 0 件更新になって落ち、削除ごと巻き戻る。

引き取ってよいのは `BLOCKING` だけ。ユーザー削除と `READY_TO_PURGE` への遷移は同一
トランザクションなので、**`BLOCKING` が残っている = 利用者はまだ消えていない**。
`READY_TO_PURGE` と `NEEDS_REVIEW` は既に消えた後なので、新しい退会要求が乗ってよい
状態ではない。

トークンの失効は本数に比例して時間がかかるので、1 ページ消すごとに期限を延ばす。
延ばせなかった (= 引き取られた) 時点で止める。

定期実行も同じ期限で掴む。以前は「直前に試したものを 5 分飛ばす」だけだったので、
処理が 15 分を超えると次の cron が同じ行を掴めた。今は掴んだ側が期限を延ばし続ける。

**引き取るときは印そのものを差し替える。** 期限だけを進めても、前の持ち主は自分の
`intentId` を握ったままなので、期限切れの後に息を吹き返せば延長に成功してしまい、
引き取った側と同時にトークンの失効と purge を進められる。相手が別人と判定して人の
確認待ちに移した後でさえ消しにいける。差し替えれば、前の持ち主の以後の更新は
延長も、状態の変更も、印の削除も、1 件も通らない。

片付けは印を握ってからでないと始めない。退会を始めた処理から続けて呼ぶ場合は
自分の印で押さえ直し (待っている間に引き取られていることがある)、定期実行からは
新しい印で引き取る。掴めなければ何もしない。

消す直前にもう一度握りを確かめる。この確認と Forgejo への DELETE の間は開いたままで、
そこは閉じられない (Forgejo 側に条件付きの削除が無い)。開いている幅を 1 往復に
縮めるところまでが、こちら側でできること。

期限切れの `BLOCKING` は cron が拾って外す (`releaseExpiredGitAccountDeletionBlocks`)。
外す前に**利用者が本当に生きているかを確かめる**。消えているのに `BLOCKING` が残って
いるなら、同一トランザクションの前提が崩れているか、この経路の外でユーザーが消されて
いる。どちらも自動で判断してよい状態ではないので `NEEDS_REVIEW` に回す。

印がある間は資格情報を発行できない (`assertGitAccountNotBeingDeleted`)。これが無いと、
1 と 3 の隙間に発行された 1 本が purge の失敗と重なって生き残る。監査ログやログ出力
だけに頼らないのは、それら自体が失敗すると手掛かりが消えるため。

3 で掃き直すのは、印を立てる前に始まっていた発行が 1 と 2 の間に着地しうるため。

3 が失敗しても投げない。アクセスは断ててあり、Beutl 側の削除は既に確定していて
戻せない。印が残るので `retryPendingGitDeletions` が拾って再試行する。消化は
`beutl-web-api` の cron (15 分ごと) で行う。利用者のリクエストの中でやると、その人の
応答が遅くなるうえ、次の退会が起きるまで残り続ける。

1 と 3 の間に 2 を挟むのは、どちらの向きの失敗でも取り返しがつくようにするため。
1 の後で 2 が失敗しても、アクセスは既に断たれていて、リポジトリは残っている。
先に purge してしまうと、2 が失敗したときに「アカウントは残っているのにリポジトリだけ
消えた」という戻せない状態になる。

対応表が失われていても諦めない。合成メール (`{userId}@users.noreply.{host}`) は userId
から決まるので、`GET /users/search?q={email}` で Forgejo 上のユーザーを引き当てられる
(ユーザー名と無関係なメールでも引けることを実測済み)。ここを飛ばすと、DB の復元ずれで
対応表が消えたユーザーが、退会後もトークンを使い続けられる。

逆に、対応表がある場合も名前だけでは動かない。**削除は取り返しがつかない**ので、
通常操作より 1 つ厳しく、id とメールの両方が本人のものであることを確かめる。片方でも
食い違えば中止する。復元ずれで同じ名前が別人を指しているとき、そのまま進めると
別人のトークンを全部失効させてリポジトリごと消してしまう。

#### 消し終えても行は残す

purge が通ったら phase を `PURGED` にして**行は残す**。

**Forgejo だけを退会前の時点に戻すと、ユーザーもリポジトリも端末のトークンも復活する。**
そのとき beutl-web 側には利用者も進行中の行も残っていないので、消したという記録が
無ければ復活に誰も気付けない。git と LFS は Caddy を素通りして Forgejo が直接認証
するので、復活したトークンはそのまま使える。「消した」ことを持ち続けるのは、
組にして戻せなかった場合に気付くための唯一の手掛かり。

復元の後に全件を見終わったかは、数えて確かめられる。**掴んだ時点では
`lastAttemptAt` を進めない** (失敗も進めない) ので、この値が「見終わった時刻」を
意味する。

```sh
pnpm run git:restore-generation --nonce '<復元時に出力された値>'   # 復元直後に 1 回
pnpm run git:reconcile-status --proof '<同じ値>'                   # 一巡した後
```

**判定は時刻ではなく世代で行う。** 復元のたびに `GitRestoreGeneration` に 1 行足し、
確認した墓標には「どの世代で確認したか」を書く。時刻で比べると、VPS と Worker と
CockroachDB の時計のずれや、同じ秒に起きた復元前の確認を取り違える。世代の一致なら
時計は要らない。世代がそのデータベースに登録されていること自体が、確かめた相手が
本番であることの裏付けにもなる (別の綺麗な DB を指しても通らない)。

今の世代で確認していない墓標は、確認の間隔 (6 時間) を待たずに見直す。待たせると、
復元の後 git を止めている時間がその間隔ぶん延びる。

数えるのは 1 つのトランザクションの中で。別々に数えると、その間に `PURGED` から
`NEEDS_REVIEW` へ移った行を、片方では移動後・もう片方では移動前として数え、
どちらも 0 に見える。

**決着していない退会も数える。** `READY_TO_PURGE` は「Beutl 側は消えたが Forgejo を
消し切れていない」状態で、退会したはずのアカウントと端末のトークンがそのまま
生きている。墓標だけを見ていると、これが残っていても 0 に見える。`BLOCKING` も
「どうなっているか分からない」ので残っている間は開けない。

証拠には**有効期限**を入れる。作った後に状態が悪くなっても署名は変わらないので、
示せるのは「その時点では終わっていた」ことだけ。短く切って、作ったらすぐ使う。

控えの無い墓標 (`forgejoUsername` が null) は照合しようがない。対象から外すのでは
なく `unresolved` として数える。黙って除くと、照合できないものが残ったまま 0 に
見える。

証拠は ed25519 の署名で、**署名鍵は beutl-web 側にしか無い**。git-server は公開鍵で
検証するだけなので、あちらの `.env` を読める人でも証拠は作れない。共通鍵だと
「事故を防ぐ仕掛け」にはなっても「確認を飛ばせない証明」にはならない。

署名の中身には**確認した相手**を入れる。世代の登録はどの `DATABASE_URL` に対しても
できるので、これが無いと、うっかり staging を指して登録・確認した空の結果で本番向けの
証拠が作れてしまう。ホスト名だけでは足りない (同じホストに本番と staging が別の
データベースとして載っていることがある)。`host:port/database` と、配備側で決めた
環境の名前の両方を入れ、git-server 側も期待する値と突き合わせる。

定期実行は 1 回で見るものが無くなるまで回す (`drain`)。処理した件数・消し直した
件数・失敗した件数・残りをログに出す。

墓標は定期実行が数時間おきに引き直す (`reconcileGitAccountDeletionTombstones`)。
控えた名前で引き、見つからなければ合成メールでも引く (復元先で名前が違うことがある)。
退会そのものの経路でも同じで、**名前で見つからない場合と、見つかった相手が別人だった
場合の両方**で合成メールを引き直し、引き当てた相手を墓標に控える。控えないと、
その墓標が誰を指すのか分からなくなり、復活の照合から外れる。そのうえで、

- 居なければ何もしない
- **Beutl 側の利用者が復活していれば**、戻ったのは beutl-web の方。その人は生きて
  いるので**消さない**。人の確認に回す
- 控えた id と合成メールが一致すれば、復活したものとして消し直す
  (`git.accountResurrected` として監査に残る)
- id かメールが違えば、名前を再利用した別人。触らない

墓標があると資格情報を発行できなくなるわけではない。`PURGED` は決着済みなので、
発行を止めるのは `BLOCKING` / `READY_TO_PURGE` / `NEEDS_REVIEW` の 3 つだけ。
beutl-web 側だけを戻して利用者が復活した場合、その人は新しく作り直せる。

墓標は**復元しうる最も古い控えより長く**残す必要がある。消してしまうと、その時点
より前に戻された場合に検出できない。世代の保持期間 (`KEEP_GENERATIONS`) より短く
刈らないこと。

一方で、墓標は退会した人の `userId`・Forgejo のユーザー名・Forgejo の id を持ち続ける。
自動では刈らない (保持期間はこちらのリポジトリからは分からず、短く刈ると検出できなく
なる) ので、**保持期間を過ぎたものを定期的に落とす運用が要る**。世代の保持が 30 日なら、
例えば次のようにする。

```sql
-- 復元しうる最も古い控えより後に消したものだけを残す
DELETE FROM "GitAccountDeletion"
WHERE "phase" = 'PURGED' AND "purgedAt" < now() - INTERVAL '35 days';
```

日数は `KEEP_GENERATIONS` × バックアップ間隔より**長く**取ること。短くすると、
まだ戻せる時点の退会を検出できなくなる。

#### 片付け待ちを見る

自動で消化されるのは `READY_TO_PURGE` だけ。`NEEDS_REVIEW` は人が判断する。

気付く経路は 2 つある。専用の画面は作っていないが、**行が `NEEDS_REVIEW` に落ちた
時点で監査ログに残す** (`git.accountNeedsReview`) ので、管理画面の監査ログを
その action で絞れば一覧できる。加えて cron が毎回件数を数え、0 でなければ
`console.error` に出す (Worker のログを監視していれば拾える)。期限切れの印を外した
場合も `git.deletionMarkerReleased` として残す。

中身を見るときは DB を直接読む。

```sql
-- 片付いていない退会
SELECT "userId", "phase", "forgejoUsername", "forgejoUserId",
       "leaseUntil", "attempts", "lastAttemptAt", "lastError"
FROM "GitAccountDeletion"
ORDER BY "createdAt";
```

`BLOCKING` のまま `leaseUntil` が過去になっている行は、cron が次に拾って外す。
外れないまま残る場合は cron が動いていないので、先にそちらを確かめる。手で外すのは
**利用者が生きていることを確かめてから**。

```sql
-- 利用者が生きているか
SELECT EXISTS (SELECT 1 FROM "User" WHERE "id" = '...');

-- 生きているなら外してよい (資格情報を発行できるようになる)
DELETE FROM "GitAccountDeletion" WHERE "userId" = '...' AND "phase" = 'BLOCKING';
```

`NEEDS_REVIEW` が出たら、Forgejo 側で何が起きているかを確かめる。

- **控えの名前が別人になっている** — 元のユーザーが復元で消えたか、名前が再利用された。
  Forgejo に元のユーザーが居ないことを確かめたら、行を消してよい
- **一時的な障害が続いていた** — Forgejo が復旧したら `READY_TO_PURGE` に戻す。
  次の定期実行が拾う

```sql
-- 再試行させる
UPDATE "GitAccountDeletion" SET "phase" = 'READY_TO_PURGE', "attempts" = 0
WHERE "userId" = '...';

-- 片付いたと確認できたので閉じる
DELETE FROM "GitAccountDeletion" WHERE "userId" = '...';
```

**行を消す前に、Forgejo 側にユーザーが残っていないことを必ず確かめる。** 残ったまま
消すと、端末のトークンが生きたまま誰も気づけなくなる。

### 5. トークンは端末ごとに 1 本持てる

トークンを 1 本に固定すると、ある端末で発行した瞬間に他の端末の資格情報が切れる。
Forgejo は名前が違えば何本でも保持できる (実機で確認済み) ので、端末名をラベルにして
複数本を並存させる。失効は 1 本ずつで、他の端末には影響しない。

一覧表示のたびに Forgejo へ問い合わせると、画面を開くだけで管理 API への往復が増える。
表示に必要なメタ情報 (ラベル・トークン id・末尾 8 文字・発行日) は `GitCredential` に控える。
Forgejo を触るのは発行と失効のときだけ。平文は控えない。

失効は名前ではなく Forgejo 側のトークン id で行う。Forgejo はトークン名に空白や
スラッシュを許すため、名前を URL パスに載せる形は避ける。

歯止めとして、ラベルは 50 文字まで (Forgejo は 255 文字を超えると 422 ではなく 500 を返す)、
1 ユーザーあたり 20 本までとしている。

#### 控えと Forgejo がずれた場合

`GitCredential` は Forgejo と自動同期しない。運用者が Forgejo 側でトークンを直接
削除すると、控えだけが残る。そのとき起きることは 2 つで、どちらも致命的ではない。

- 一覧に使えないトークンが並ぶ
- 20 本の上限判定がその分厳しくなる

回復はダッシュボードで失効を押すだけでよい。失効は Forgejo の 404 を許容して控えを
消すので、通常の操作がそのまま片付けになる。逆向きのずれ (Forgejo にあって控えに無い)
は、beutl-web 以外がトークンを作らない限り起きない。

#### 同時操作

**同じラベルの二重発行。** Forgejo にトークンを作ってから控えを書くので、同じラベルで
2 本同時に来ると Forgejo 側には 2 本でき、片方が `GitCredential` のユニーク制約で落ちる。
そのままだと控えに無いトークンが Forgejo に残るため、DB への書き込みが失敗したら
作ったトークンを消してから重複エラーとして返す。

その取り消し自体が失敗した場合は、`git.credentialOrphaned` として監査に残す。控えが
無いトークンは一覧に出ないので利用者からは失効できず、記録が無ければ誰も存在に
気付けない。退会が最後まで通れば purge 直前の掃き直しで消えるが、退会が取りやめに
なった場合はそれも走らない。専用の再試行の仕組みは作っていない (発行の失敗と取り消しの
失敗が重なる頻度に対して、耐久キューを持つ割に合わない)。監査ログの `tokenId` を見て
手で消す。

### 6. リポジトリは管理者の手元で組み立ててから渡す

`.gitattributes` は**最初のコミットに入っていなければ意味が無い**。入る前に push
されると、そこへ入った数 GiB の動画は普通の git オブジェクトとして履歴に残る。
後から `.gitattributes` を足しても、既に入った履歴は LFS に移らない。作成後に
読み取り専用へ倒す仕掛けも、既に入ってしまったものは戻せない。

そこで**利用者の名前空間には作らない**。管理者の名前空間で作り、既定値を入れ切って
から譲渡する。利用者が見ることも触ることもできるようになるのは譲渡の瞬間なので、
入る前に push される隙間そのものが無い。

```
POST /user/repos                          (Sudo なし = 管理者のもの)
POST /repos/{admin}/{holding}/contents    (既定値を入れる)
      → canonical か確かめる
POST /repos/{admin}/{holding}/transfer    ({"new_owner": "<利用者>"})
PATCH /repos/{利用者}/{holding}            ({"name": "<本来の名前>"})
```

譲渡は即時で、承認待ちにはならない。リポジトリ id も変わらない (16.0.2 で実測)。

**Forgejo を触る前に (owner, name) を予約する。** Forgejo 上の不在確認だけでは、
同じ名前の作成が同時に来たときに両方が通り、両方が譲渡され、片方だけ改名に失敗して
預かり名のまま利用者の手に残る。`GitRepositoryCreation` の一意制約で後から来た方を
弾く。予約には**先に決めた預かり名**も入れる。201 の直後に落ちるとリポジトリ id は
誰も知らないので、それだけが手掛かりになる (定期実行がその名前で引き当てて控えに
載せ替える)。

**預かる名前は毎回違うものにする** (`beutl-holding-<uuid>`)。最終的な名前で預かると、
同じ名前を別の利用者が同時に作ったときに、どちらの預かりものか区別できない。
作成の応答を落とした (502/504) ときに名前で引き直すので、区別が付かないと他人の
預かりものを自分の利用者へ渡してしまう。一意な名前なら、引けたものは自分のものだと
言い切れる。渡した後に本来の名前へ直す。

既定値を入れられなかった場合と譲渡に失敗した場合は、預かったまま畳む。**これは
他人のリポジトリを消すのとは違う。** 直前に自分の名前空間へ作ったもので、利用者は
まだ触れない。ただし **id で今の姿を確かめてから**消す。名前で消すと、その名前が
別のものに渡っていた場合に巻き添えにする。消せなかったときは控えを残す。

Worker が譲渡の前に消えると、管理者の名前空間に預かったままのリポジトリが残る。
利用者からは見えないので push はされないが、**放っておくと同じ名前を永久に塞ぐ**
(次の作成が管理者側の衝突で止まる)。そこで控えには渡す先と最終的な名前も入れ、
定期実行が**渡し切る**。揃っているからと控えだけ外すと、預かったまま残り続ける。

```
SELECT * FROM "GitRepositoryRepair";
```

### 7. 直せなかったリポジトリは読み取り専用にする

リポジトリは `.gitattributes` を最初のコミットに入れて作る。これが無いと素材が LFS に
載らず、数 GiB の動画が普通の git オブジェクトとして入って後から剥がせない。

作成直後のコミットに失敗したら入れ直す。それも失敗したら **archived にして push を
止める**。Forgejo の archived は push を 403 で拒み、clone は通す (16.0.2 で実測)。
既に入っているものは取り出せるまま、壊れた状態が広がるのだけを止められる。

判断は「コミットが成功したか」ではなく **「入った結果が正しいか」**。`commitTemplates`
は既にあるファイルに触らない (利用者が意図して編集した `.gitattributes` を壊さない
ため) ので、空や書き換え済みのファイルが置かれていると、何もせずに成功する。そこで
書き込み可能なまま返すと、LFS の効かないリポジトリに push され続ける。入れ直した後は
毎回 canonical 検証を通す。

読み取り専用を外して直す経路も同じ。**外したあと確かめられなかったら必ず掛け直す。**
外したまま抜けると、一度守った状態がやり直しのたびに緩む。

読み取り専用にすることすら失敗した場合は `GitRepositoryRepair` に積む。ログだけだと、
LFS の効かないリポジトリが push を受けられる状態のまま誰にも気付かれない。控えるのは
**Forgejo のリポジトリ id**。名前は改名で変わり、空いた名前を別のリポジトリが取る
ことがあるので、名前で引き直すと別物を止めてしまう (`PATCH /repositories/{id}` は
405 なので、id で引いてから、そのとき返る名前に対して操作する)。

控えには 2 種類あり、片付いたと言える条件が違う。

| 種類 | 片付いた条件 |
| --- | --- |
| 預かりもの (`intendedOwner` あり) | 既定値が揃い、**譲渡と改名まで終わった** |
| 直し (`intendedOwner` なし) | 既定値が揃った、または読み取り専用になった |

**混ぜてはいけない。** 直った時点で控えを外すと、譲渡の前に落ちた預かりものが
管理者所有のまま追えなくなり、その名前の作成を永久に塞ぐ。だからテンプレートを
直す処理も読み取り専用にする処理も、控えには触らない。外すのは、片付いたと
判断した呼び出し元だけ。

譲渡だけ済んで改名が残っている状態も拾う。渡す先でも管理者でもない誰かが持って
いる場合は自動では決められないので、`needsReview` を立てて人に回す。

掴むときは印を差し替える。期限だけを進めても、期限切れで引き取られた側が息を
吹き返せば譲渡や控えの削除を続けられる。

**Forgejo を触る前にも毎回、握っていることを確かめる。** DB の書き込みだけを印で
守っても、引き取られた側が unarchive・commit・transfer・rename・削除を続けられては
意味が無い。前面の作成処理も、控えを積んだ後に必ず握ってから進む。積んだ瞬間から
定期実行が掴めるので、握らずに進めると同じ相手を 2 つで譲渡できる。

**引き取られたと分かったら、後始末もしない。** 失敗の後始末として預かりものを畳む
経路があるが、握りを失っている場合、その相手は既に引き取った側が渡そうとしている
ものかもしれない。通常の失敗と同じに扱うと、新しい持ち主の作業を壊す。

控えを積めなかった場合 (DB に書けなかった) は、預かりものを畳んでから投げる。
控えが無いまま残すと、無作為な名前のリポジトリが管理者の名前空間に残り、誰も
片付けられない。

本来の名前が既に埋まっていて改名できない場合は、何度やり直しても通らない。
15 分ごとに回し続けずに `needsReview` を立てる。中身は揃っていて所有者も正しいので、
残るのは「預かり名のままになっている」ことだけ。

控えるのは**テンプレートを書く前**。例外を捕まえられる失敗だけを積んでいると、
201 の後に Worker ごと消えた場合に何も残らない。先に積んでおけば、どこで落ちても
定期実行が拾う。201 が返ってから控えを書くまでの隙間だけは埋められない
(リポジトリ id はその応答で初めて分かるため)。

消さないのは、作成の 201 と「作成直後の状態」を原子的に得る手段が無いため。控えた
SHA は既に誰かの push 後のものかもしれず、空に見えるだけの誰かのリポジトリを消し
かねない。

戻す経路は**同じ名前でもう一度作る**こと。既存の判定でテンプレートが揃っていなければ
修復として扱い、archived を外してからコミットする (contents API は archived だと 423 を
返すので、外すのが先)。直せたときだけ push できる状態に戻る。

## 配備の順序

マイグレーションより先に Worker を出すと、新しいテーブルや列を前提にした経路が本番で
落ちる。この分岐で言えば、資格情報の発行前に見る `GitAccountDeletion` と、15 分ごとの
cron がそれにあたる。逆にマイグレーションだけ先に当てても、古い Worker は動き続けられる
(足すだけで、消す列が無いため)。

順序は `pnpm run release` に固定してある。

1. 当てる前に食い違いを見る。相手のデータベースに入っているのにこの分岐に無い
   マイグレーションがあれば、**何も書かずに**止まる。分岐が遅れている場合と、
   相手に未マージの分岐が当たっている場合の両方がここで引っかかる
2. `prisma migrate deploy`
3. 適用し切れたことを確かめる。残っていれば Worker を配らない
4. Worker を 3 つ配る
5. 3 つの Worker が応答することと、`BEUTL_SMOKE_JWT` で
   `GET /api/v3/git/credentials` が返ることを見る。この経路はこの分岐で入った
   テーブルを読むので、当たっていなければ 200 にならない

確かめていないものは毎回出す。Web と Admin の Forgejo 用 secret (セッションが要る)、
管理画面からの削除経路、定期実行の 3 つ。`GET /api/v3/git/account` は無ければ
Forgejo ユーザーを作るので、専用アカウントを使うときだけ (`BEUTL_SMOKE_PROVISION=1`)
叩く。`pnpm run deploy` もこの順序を通る。個別の `deploy:web` などを直接叩けば
迂回できるが、それは意図して 1 段だけ回したい場合のためのもの。

`prisma migrate status` の判断材料は **stderr に出る** (prisma 7.9.1 で実測)。
stdout だけを見ると、見ているつもりで何も見ていないことになる。

## この分岐を配備するときの前提

この分岐は 11 本のマイグレーションを持ち込む。

```

20260817142000_add_git_credential
20260821070000_add_git_account_deletion
20260821090000_git_account_deletion_review_and_intent
20260821110000_git_account_deletion_lease
20260821130000_git_account_deletion_tombstone
20260821140000_add_git_repository_repair
20260822010000_git_repository_repair_handover
20260823010000_git_repository_repair_fencing
20260823020000_add_git_restore_generation
20260823030000_add_git_repository_creation
```

**development クラスタには今のところ配備できない。** このクラスタには、まだ main に
入っていない別の分岐のマイグレーションが適用されている (`20260808000000_add_ai_credit_subscription`
以降の一連。`pnpm run migrate:status` で確認済み)。`release` の 1 でそのまま止まる。

分岐自体は origin/main に追従している (`git rev-list --count HEAD..origin/main` は 0)。
遅れているのは分岐ではなくクラスタの側で、**追従では解消しない**。先に相手の分岐が
main に入るか、そのクラスタで整理されるのを待つことになる。

本番クラスタがどうなっているかはここからは確認していない (`.env` の本番接続は
コメントアウトされたままで、繋いでいない)。`release` は当てる前に必ず見るので、
食い違っていれば書き込む前に止まる。

`20260821070000` は作業の途中で 2 度書き換えたが、**最終形は初出時のバイト列に戻して
ある**。後から必要になった列と enum の値は `20260821090000` で足すので、先に適用済みの
環境でも未適用の環境でも同じ結果になる。ただし途中の版を適用した環境があると、
Prisma が持つ checksum と食い違う。

適用済みの環境は無いことを確認済み: この分岐は push されておらず、development
クラスタでも `prisma migrate status` が全て「未適用」と報告する。以後この分岐で
マイグレーションを書き換えた場合は、配備前に同じ確認をすること。

```
pnpm run migrate:status
```

順序が入れ替わったまま流すと、以後 `migrate status` が常に食い違いを報告する。
それが development クラスタで今起きていることで、後から直せない。

## Consequences

- Forgejo が持つ Issue / Pull Request / コードレビューは使えない。必要になったら
  beutl-web 側で作るか、UI 公開の判断をやり直すことになる。
- `FORGEJO_ADMIN_TOKEN` はサイト全体の管理権限を持つ。漏洩の影響が大きいので
  `wrangler secret` に置き、Caddy 側の共有シークレットと併用する。
- Forgejo の API には `size` という名前のフィールドが 2 つあり、意味が違う。混同しやすい。

  | どこ | 意味 |
  | --- | --- |
  | リポジトリ (`/repos/{owner}/{repo}`) の `size` | KiB 単位。リポジトリ本体 **と LFS の合計**。保存先が S3 でも変わらない |
  | contents API のエントリの `size` | バイト単位。LFS 管理下のファイルでは**ポインタ自身**の大きさ (百数十バイト) |

  一覧画面の合計容量は前者を使い、ファイルごとのサイズは後者なので `resolveContentSizes` が
  小さいファイルだけ中身を読んで実サイズに直す。判定はサイズだけで行い拡張子は見ないので、
  アイコンの対応表に漏れがあってもサイズ表示には影響しない。読みに行く件数には上限があり、
  超えた分はサイズを表示しない (誤った数字を出すより黙る)。

## Desktop contract

Beutl 本体の Git クライアントは `/api/v3/git/*` を使う。認証は v1 が発行する JWT
([ADR 0001](0001-v1-account-is-the-auth-backbone.md)) をそのまま使う。

| エンドポイント | 用途 |
| --- | --- |
| `GET /api/v3/git/account` | Forgejo ユーザー名とベース URL |
| `GET /api/v3/git/credentials` | 発行済みトークンの一覧 (平文は含まない) |
| `POST /api/v3/git/credentials` | トークンを 1 本発行。`{"deviceName": "..."}` が必須 |
| `DELETE /api/v3/git/credentials/{id}` | そのトークンだけを失効させる |
| `GET /api/v3/git/repositories` | リポジトリ一覧 |
| `POST /api/v3/git/repositories` | リポジトリ作成 (`.gitattributes` 込みで初期化) |

`deviceName` を必須にしているのは、省略できると起動のたびに発行するクライアントが
トークンを際限なく積み上げてしまうため。同じ名前で 2 本目を作ろうとすると 409 を返すので、
クライアントは端末ごとに安定した名前を送り、409 なら既存のものを使い回すか失効させる。

git 本体の通信 (clone / fetch / push / LFS) はこの API を通らず、Forgejo に直接 HTTPS で繋ぐ。
この API が渡すのは接続先と資格情報だけ。
